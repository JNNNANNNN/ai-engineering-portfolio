Letting an AI Agent Do Real Engineering

I gave an AI coding agent a deliberately broken chip circuit, access to the professional simulation tools, and one rule: write down every decision. Then I ran it 21 times to find out which parts of an expert’s job an AI can own, which parts it can assist with, and which parts still need a person.

The task, in plain terms

Inside a chip there are circuits made of transistors. Each transistor has a couple of dimensions you can change, like adjusting the knobs on a mixing desk. A circuit is only “done” when it passes a fixed set of tests under hot, cold, fast and slow manufacturing conditions. Here that was 48 tests.

Normally a senior engineer looks at the test results, decides which knob to turn, re-runs the simulation (which takes minutes to hours), and repeats. It is skilled, repetitive and slow. The question was whether an AI agent could run that loop itself, and how we would know whether to trust it.

How I set it up

I did not want a demo where the AI gets a clean problem and a scripted answer. The agent used the same software the engineers use, on the same shared compute cluster, with real queue waits. What I added was a working method around it.

1 · BRIEF

Register the case

What circuit, what tests, where the starting point is, two safety checks before anything runs.

2 · LOOP

The agent works alone

Run simulations → read results → pick the next change → run again. No human in the loop during this phase.

3 · DIARY

Tag every decision

Each meaningful choice is logged under one of six question types, including who should ideally own that choice.

4 · REPORT

Structured write-up

Fixed template so cases can be compared, plus a full appendix of every round, including the wrong turns.

One rule above all others: the agent may never touch the original design. It works on a copy in a sandbox. I added this after an early scare when unexpected files appeared next to the real design. It turned out to be unrelated, but the rule stayed, and it is the first thing the method checks.

What I learned about working with an agent

Make it keep a diary, not just an answer

The first report I received only stated the final fix. I changed the template so every run must include each round: what it tried, why, what it saw, what it concluded. The reversed theories and failed attempts turned out to be the most valuable part, because they are exactly what a future engineer or a future AI needs to avoid repeating.

Two independent agents agreeing is a real signal

On the dead circuit, both models started from nothing and landed on the same three parts and the same mechanism. The numbers differed slightly because their search paths differed. That is a cheap cross-check I now use on purpose.

“I could not do it” has to come with evidence

The one failure was the most instructive run. The agent did not quietly stop; it measured four different approaches, showed they all traded one problem for another at a fixed ratio, and then wrote down which ideas remained untested. A person can pick that up immediately.

The agent does not get to sign off

Several “passing” results had safety margins of only a few millivolts. Every report flags this and recommends a further statistical check before anyone accepts the change. Writing the fix back into the real design is a separate, human-approved step by design.

The real deliverable: who should own which decision

The project was commissioned to answer a management question, not to fix circuits: when an AI agent is embedded in this workflow, what should be automated outright, what should the agent decide, and where must a human stay? After tagging every decision across 21 cases, a stable pattern emerged.

OwnerKind of workWhy
Plain automationPreparing files, applying standard settings, recomputing dependent values, consistency checksDeterministic and already correct in existing code. I extracted these into a small library so the agent calls them instead of re-deriving them.
The AI agentReading results, forming a theory of what is wrong, choosing what to try next, recognising when it is stuckNeeds judgement over messy evidence, and the agent showed it could do this, including correcting its own mistakes.
A human expertSupplying knowledge that cannot be inferred from data, accepting a thin margin, deciding whether a stall is worth more effort, final approvalThese are accountability decisions, not search problems.

What I built and handed over

  • A reusable agent “skill”: one folder that encodes the four-phase method, the diary format, the report template and the sandbox rule. Drop it into a new project and the agent runs cases the same way.
  • A small helper library for the mechanical steps, carved out of an older in-house tool after reading its source and keeping only the parts with no hidden dependencies.
  • An archive of 21 runs with diaries, reports and results, under version control.
  • Comparison reports across the six sabotage cases and the two models, written for the team building the company’s wider AI design platform.

Limits worth stating

  • One circuit type was tested thoroughly; others were run but not to the same depth.
  • Most of the wall-clock time was simulation queueing on a shared cluster, not the AI thinking.
  • The agent proposes; a person still applies. That is deliberate, not a gap.
