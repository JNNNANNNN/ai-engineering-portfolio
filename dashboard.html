Shipping a Department Dashboard with an AI Pair

A 40-person engineering department had its work scattered across five company systems. In about four weeks, working as a team of one plus an AI coding agent, I took a dashboard from a first sketch to a production deployment that people use daily and that writes their actions back into the systems of record.

The problem, in plain terms

To answer “what do I owe this week and what did we agree in the last meeting?”, an engineer had to log into four or five separate systems, each with its own vocabulary and none of them showing a view for one person or one department.

Management also set a bar for any internal AI or dashboard project: it must not be a read-only mirror. People have to be able to act from it, and the action must flow back to the original system so the next refresh reflects it. That one sentence shaped the whole design.

How the AI and I split the work

The agent wrote most of the code. I spent my time on the things that decide whether an internal tool survives: understanding the data, measuring the real systems, deciding what to trust, and talking to the people who would use it.

What I did

  • Interviewed users and reverse-engineered the data model from screenshots of the source system.
  • Wrote a plain-language question list for the IT team about which APIs existed and what they returned.
  • Made the four decisions that framed everything: what counts as “our work”, which two views matter most, who may upload, and that all data access goes through one adapter layer.
  • Measured every API’s real latency and reliability before designing around it.
  • Reviewed every screen with real input, not simulated clicks, after one bug slipped through automated checks.

What the agent did

  • Built the single-file prototype with a mock data layer in one session, so users saw real screens before any integration existed.
  • Swapped the mock for the real gateway without touching the UI, because the adapter boundary was agreed up front.
  • Wrote the background jobs, the identity layer, the write-back proxies, the container build and the deployment scripts.
  • Kept a running set of project notes: decisions, measured numbers, dead ends and the reasons behind them, so each new session started with context instead of re-discovery.
  • Produced the hand-over documents and even the prompt a future AI can use to rebuild the deployment package.

What was built

The site stores no business data of its own. A small service pulls snapshots from the company’s API gateway on a schedule, serves them after checking who is asking, and forwards two kinds of edits using that person’s own identity.

Lessons that only showed up in production

Measure before you design

One API returned everything in about a second. The one holding the data we actually needed took 20–45 seconds per project and sometimes returned a hollow “success”. Instead of fighting it, the slow calls moved to a nightly job that validates each record before it is allowed into the cache. The page loads in milliseconds.

Refresh at the source’s real speed

The upstream data was itself only refreshed every 30 minutes. A “live” button would have cost three minutes and shown the same data. So the board refreshes every 15 minutes, shows its snapshot time, and marks edits as pending until they appear.

Never overwrite good data with bad

Twice an upstream error produced a valid-looking but empty result, and the page cheerfully showed “nobody has anything to do”. Every job now refuses to write if the count is zero or drops by more than half, and each data section keeps its last good version, with a reason, if its own fetch fails.

Do not probe a live system with writes

While exploring an API, the agent sent a test request with deliberately bad parameters to see what the validation did. The system did no validation and wrote the bad record. That became a standing rule in the project notes: read-only probes only, and the rule is now part of how I brief any agent on a production system.

Identity was the hardest design decision. Both write-capable systems record “who did this” from the key used. One shared key would have credited every edit to one person. The answer was for each user to paste their own personal key once, which the service verifies and never stores, and to use only that key for that person’s edits.

How I work with the agent

  • Decisions live in notes, not in chat. Every measured number, every “we tried this and it failed”, every user preference is written to a persistent project note the agent reads at the start of each session. Four weeks of work never had to be re-explained.
  • Prototype before integration. A mock data layer let users react to real screens in day one and let the agent build the UI without waiting on IT.
  • Boundaries first, code second. The adapter rule (UI never calls an API directly) was set before any code existed. It is why the integration later took hours, not days.
  • Verify with real input. Automated clicks missed a focus bug that a human found in seconds. Now every screen gets a human pass.
  • Hand-over is part of the build. Each program file begins with the reason it exists, and the hand-over document is written for the next maintainer, human or AI.

Limits worth stating

  • Freshness is bounded by the upstream 30-minute refresh; the page says so rather than hiding it.
  • One write path has no delete; a wrong submission must be corrected in the source system.
  • Workload figures only cover the sub-team that reports time allocation; others show “not reported”, not a guess.
