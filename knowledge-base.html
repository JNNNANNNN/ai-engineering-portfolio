Making Company Knowledge Readable by People and AI

An engineering team had a good internal wiki that only a browser could read. I rebuilt it as one trusted database that generates everything else: pages for people, indexes for AI agents, and an assistant that answers engineers’ questions with citations and says plainly when the answer is not there. Then I measured how well it answers, sixty questions at a time.

The problem, in plain terms

The team designs a chip that drives large 4K displays. The chip is built from about thirty components, each with thousands of settings. Knowing which setting to change, and whether the documentation about it is still accurate, is the daily job.

The existing wiki was good, but it was a web app only. Nothing in it could be read by an AI agent without scraping. It had no link to the source design, which is the only real truth when documents are stale. And it did not say how far to trust any given sentence, even though much of it had been inherited from the previous chip.

One trusted layer, everything else generated

The principle, borrowed from a colleague’s knowledge platform and applied strictly: there is exactly one place the truth lives, and one command rebuilds everything from it. Nobody edits generated output. If a page is wrong, you fix the source and rebuild.

Designing for an AI reader

Most of what I learned on this project is about how to hand knowledge to an AI agent so that it behaves well.

Give it one entry document, not a folder

An agent dropped into a folder will scan everything and still miss the point. Instead there is a single entry file that says: here is what this is, read these indexes in this order, here is the vocabulary for how much to trust things, here are the rules. The assistant on the website follows the same file.

Trust is a field, not a feeling

Every entry carries the wiki’s own status: verified, unverified-seed, or placeholder. Every component carries a documentation status. The agent is told what each level permits, down to “a placeholder may never be stated as fact”.

Link claims to evidence

Wiki entries already mentioned source files and line numbers in passing. Those references are extracted into a map, so when documentation and source disagree, the assistant can read the exact lines and say which is which, with the version attached.

Bound the agent

The assistant may make at most 20 lookups and run about two minutes per question. It streams each lookup to the user as it goes, must label inferences as inferences, and when it reaches the limit it answers with what it has and says so.

Rule four in the entry document: when the wiki and the source disagree, show both with their sources. Do not pick a side on the user’s behalf.

Measuring the assistant

An assistant that sounds confident is easy to build. I wanted to know how often it was right, how often it admitted ignorance, and how much it cost per answer. Three batches of twenty questions were scored on five axes: correctness, actionability, honesty and labelling, completeness, and concision. The rubric, every answer and every lookup trail are published together.

The evaluation found documentation bugs, not just assistant bugs. Each batch produced a list of gaps the assistant ran into: settings missing from the tables, an entry whose value may have flipped between design versions, a range two components appear to share. Those went back to the owners as tickets. The questions about features the chip does not have, it correctly declined to answer.

The website around it

  • Beginner and expert modes. Beginners get general concepts, a guided reading route and a “read this first” tab per component. Experts see only the specification and settings. A third mode is a classic wiki layout.
  • Editing without a database. Editors add components, topics and entries through forms that write straight to the trusted base; a save triggers the rebuild in the background so pages and AI indexes never drift apart.
  • Identity from the company gateway. A user pastes a personal key; the server resolves it to a person and department and grants editing by department. Keys are never stored.
  • Gaps become work items. When the assistant cannot answer, the editing page offers to turn that question into an entry, a ticket for the owner, or a documented decision not to fix, with undo.

How I worked with the AI to build it

  • Read before building. The first day was spent reading the colleague’s platform and writing down explicitly what to borrow and what not to copy, because the two data sets had different natures.
  • Small, testable tools. The pipeline is five short scripts and one orchestrator, each with a clear input and output. The agent could extend one without understanding all of them.
  • Let the AI find its own bugs. The source-design parser missed a whole class of connections at first. Rather than guess, I had the agent print what it saw at the failing line, which exposed a one-character assumption in the pattern.
  • Evaluate like a product, not a demo. Sixty scored questions with a published rubric turned “it seems to work” into numbers, and turned the assistant into a tool for finding documentation gaps.
  • Persistent notes. Decisions, measured costs and gotchas live in project notes the agent reads each session, so four weeks of context was never re-explained.

Limits worth stating

  • The scorer was the same family of model as the assistant and may share its blind spots; correctness was spot-checked, not exhaustively verified.
  • Some line references inherited from the wiki point at an older design version than the current scan.
  • The assistant runs on one shared gateway account; per-user accounting is the obvious next step.
